# Updated AIRTP Protocol Specification with AIRTP.py Integration

# Abstract

The AI Realtime Transport Protocol (AIRTP) defines a session-oriented application protocol for interactive Artificial Intelligence systems.

AIRTP provides a provider-independent communication model that separates application logic from transport implementations and provider-specific APIs.

Rather than exposing transport mechanics to applications, AIRTP presents a consistent session interface that manages capability negotiation, logical message exchange, streaming, provider adaptation, and orderly session shutdown.

The protocol is transport agnostic and may operate over WebSocket, HTTP streaming, local IPC, or future communication mechanisms without requiring changes to application code.

AIRTP.py provides a single-file reference implementation of the protocol, including a websocket transport, OpenAI provider adapter, capability negotiation, message chunking, and runtime state management.

---

# 1. Design Goals

AIRTP is designed around six primary objectives.

1. Session-oriented communication
2. Provider independence
3. Transport independence
4. Deterministic logical messaging
5. Explicit capability negotiation
6. Extensible protocol evolution

---

# 2. Protocol Model

AIRTP operates as a layered protocol.

```text
Application
      │
      ▼
AIRTP Session
      │
      ▼
Provider Adapter
      │
      ▼
Transport
      │
      ▼
Remote Endpoint
```

Applications communicate only with AIRTP sessions.

Provider adapters isolate vendor-specific APIs.

Transport implementations move serialized protocol messages without interpreting protocol semantics.

AIRTP.py implements this layered model in a single-file architecture, maintaining the same separation of concerns.

---

# 3. Session Model

Every communication channel is represented by a Session.

A session maintains:

* Session Identifier
* Negotiated Capabilities
* Logical Sequence State
* Provider Adapter
* Transport Binding
* Runtime Metadata

The session is responsible for coordinating the complete lifecycle of a logical connection.

AIRTP.py implements the session via the `AIRTPSession` class, which manages session lifecycle, capability negotiation, envelope construction, and more.

Applications do not communicate directly with transports or providers. They interact only through the session interface.

---

# 4. Session Lifecycle

```text
Session Created
        │
        ▼
Transport Connected
        │
        ▼
Capability Negotiation
        │
        ▼
Provider Initialization
        │
        ▼
Session Ready
        │
        ▼
Logical Message Exchange
        │
        ▼
Graceful Shutdown
```

Each stage has clearly defined responsibilities.

In AIRTP.py, the `AIRTPSession.start()` method initiates transport connections and performs capability negotiation with the provider. Logical message exchange and runtime logic are handled by the runtime state machine.

---

# 5. Logical Messages

AIRTP exchanges logical messages rather than transport events.

Applications send requestsand receive complete responses.

Transport fragmentation, streaming events, and provider-specific message formats remain internal implementation details.

A logical message consists of:

```text
Envelope
    │
    ├── Metadata
    ├── Sequence
    ├── Message Type
    └── Payload
```

AIRTP.py implements envelope construction via the `EnvelopeFactory` class, which produces protocol-compliant message envelopes.

---

# 6. Envelope Format

Every AIRTP message is represented by an envelope.

Example:

```json
{
  "protocol": "AIRTP/0.1",
  "message_type": "MODEL_REQUEST",
  "message_id": "123e4567-e89b-12d3-a456-426655440000",
  "transport_contract": {
    "chunk_visibility": "hidden",
    "assembly_state": "complete",
    "semantic_role": "user_message"
  },
  "payload": {
    "content": "Hello, world!"
  }
}
```

Required fields:

| Field            | Description               |
|-----------------|---------------------------|
| protocol         | AIRTP protocol version    |
| message_type     | Logical message type      |
| message_id      | Unique message identifier    |
| transport_contract | Transport-specific metadata   |
| payload         | Application payload       |

AIRTP.py uses this envelope format to encapsulate logical messages, enabling deterministic sequencing and reliable transport.

---

# 7. Message Types

AIRTP defines logical protocol message categories.

## MODEL_REQUEST

Represents a complete logical application request.

Generated by the `EnvelopeFactory` in AIRTP.py when sending user input to the provider.

---

## DELTA

Represents an incremental logical response during streaming.

Identified and processed by the `AIRTPRuntime` class when receiving streaming chunks of output from the provider.

---

## PROVIDER_DONE

Indicates provider output cessation.

In AIRTP.py, when a `response.done` event is received from the provider, the runtime evaluates whether the logical artifact is complete or if a continuation is required.

---

## ERROR

Represents protocol, transport, provider, or application failures.

AIRTP.py handles errors by detecting `error` events in provider messages and raising runtime exceptions.

---

# 8. Capability Negotiation

Capability negotiation occurs immediately after the transport has been established.

Capabilities describe protocol behavior rather than provider features.

Typical negotiated capabilities include:

* streaming
* chunking
* compression
* binary payloads
* protocol revision
* future extensions

In AIRTP.py, the `CapabilityNegotiator` and `OpenAIRealtimeAdapter` classes handle capability negotiation by sending the AIRTP protocol contract as part of session initialization.

---

# 9. Sequencing

Every logical message contains a monotonically increasing sequence number.

AIRTP.py preserves logical sequencing by assembling messages in order and ensuring that all logical segments are delivered to the requesterin the order received.

Though individual transport events may not have explicit sequence numbers, the runtime manages logical continuity internally.

---

# 10. Streaming

AIRTP separates logical streaming from transport streaming.

A provider may emit multiple transport events while AIRTP exposes either:

* incremental logical chunks, or
* one completed logical response

depending on the negotiated capabilities and application interface.

AIRTP.py implements streaming by listening for incremental `delta` events from the provider. The `AIRTPRuntime` class assembles and delivers them in sequence.

---

# 11. Provider Adapters

Provider adapters translate between AIRTP and provider-specific APIs.

Responsibilities include:

* authentication
* session initialization
* request translation
* event translation
* response assembly
* graceful shutdown

In AIRTP.py, the `OpenAIRealtimeAdapter` class acts as the provider adapter, isolating OpenAI-specific behaviors and issuing continuation requests when needed.

---

# 12. Transport Independence

AIRTP intentionally makes no assumptions regarding the underlying transport.

Supported transports may include:

* WebSocket
* HTTP Streaming
* TCP
* Unix Domain Socket
* Named Pipe
* Local IPC
* Future transport implementations

Every transport exposes a common interface.

In AIRTP.py, the `WebSocketTransport` class implements the transport layer using WebSocket over TLS, handling connection establishment, message sending, and receiving.

---

# 13. Error Model

AIRTP categorizes failures according to architectural layer.

## Transport

* connection failure
* TLS failure
* timeout
* authentication failure

## Protocol

* malformed envelope
* invalid sequence
* unsupported capability
* negotiation failure

## Provider

* invalid request
* provider unavailable
* quota exceeded
* unsupported model

## Application

* invalid input
* unsupported operation

AIRTP.py detects and handles errors at each layer, raising exceptions when needed.

---

# 14. Session Shutdown

Orderly shutdown follows a consistent sequence.

```text
Application

      │

Session Close

      │

Provider Shutdown

      │

Transport Close

      │

Session Destroyed
```

Transport failures may terminate a session immediately.

AIRTP.py implements graceful shutdown by closing the WebSocket connection and terminating the session.

---

# 15. Versioning

Every AIRTP envelope contains a protocol version.

Future revisions should negotiate compatibility during capability exchange.

In AIRTP.py, the protocol version is defined by `AIRTP_VERSION`, currently `"AIRTP/0.1"`, and is included in each message envelope.

---

# 16. Security Considerations

AIRTP separates protocol security from transport security.The transport layer is responsible for:

* encrypted communication
* endpoint authentication
* credential transmission

The protocol layer is responsible for:

* envelope validation
* sequence validation
* capability validation

Provider credentials must never appear inside AIRTP protocol payloads.

In AIRTP.py, the `WebSocketTransport` handles TLS and authorization headers, while the protocol logic handles validation and continuity.

---

# 17. Future Extensions

AIRTP is intentionally designed for protocol evolution.

Potential future capabilities include:

* multiplexed sessions
* resumable streams
* adaptive chunk sizing
* binary framing
* compression negotiation
* distributed routing
* protocol plugins
* congestion awareness

Capability negotiation enables these features while preserving compatibility with existing implementations.

AIRTP.py is built around this extensible framework, allowing future enhancements through protocol evolution.

---

# 18. Reference Implementation

The AIRTP.py reference implementation demonstrates the protocol using a modular architecture consisting of:

* Session management (`AIRTPSession`)
* Provider adapters (`OpenAIRealtimeAdapter`)
* Transport implementations (`WebSocketTransport`)
* Capability negotiation (`CapabilityNegotiator`)
* Logical message assembly (`ChunkManager` and `EnvelopeFactory`)

The implementation serves as both a working prototype and a platform for future protocol experimentation.

---

# 19. Guiding Principle

> Applications should communicate with a protocol—not with a provider.

AIRTP treats AI communication as a protocol engineering problem.

Applications depend only on the AIRTP session interface.

Provider adapters isolate vendor-specific APIs.

Transport implementations isolate networking concerns.

By maintaining these boundaries, AIRTP provides a reusable foundation for interoperable AI communication while allowing transports, providers, and protocol implementations to evolve independently.
